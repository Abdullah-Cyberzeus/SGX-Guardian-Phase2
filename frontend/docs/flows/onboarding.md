| **Goal** | Successfully pair Guardian hardware, create an account, understand DID identity, optionally create first Circle, and land on the Dashboard |

## **Step-by-Step Narrative**

### **Step 1 — Welcome Screen (OB-01)**

Marcus opens the app for the first time. He sees the SG-X Guardian welcome screen — dark background, Cervais brand, the Guardian logo, and a brief value proposition: *"Your SG-X Guardian. Secured. In your hands."*

Two options: **Get Started** (primary CTA, purple button) and a subtle **Learn More** link. Most users tap Get Started immediately.

**Design note:** This screen must load in under 1 second. If the app is still initializing, show a branded splash screen (SYS-02) before this screen appears. Do not show a loading spinner on the Welcome screen itself.

---

### **Step 2 — Hardware Pairing (OB-02)**

Marcus is prompted to pair his SG-X Guardian device. Two methods are presented with equal visual weight:

* **Scan QR Code** — Activates the browser camera. The QR code is on a sticker on the Guardian hardware.
* **Enter Serial Number** — Manual text input for situations where the camera is unavailable or the QR sticker is damaged.

**Design note:** The browser camera permission dialog will appear when the user taps "Scan QR Code." This is a system-level dialog we cannot style. We should add a line of helper text: *"You'll need to allow camera access to scan the QR code"* — so Marcus is not surprised.

**Edge case — Camera permission denied:** If the user denies camera access, show an inline error with instructions for re-enabling camera access in their browser settings. Provide a direct link to switch to the serial number method.

---

### **Step 3 — Connecting (OB-03)**

After the QR scan or serial entry, the app sends a pairing request to the Guardian hardware over the local network. Marcus sees a loading screen: *"Connecting to your Guardian..."* with a subtle animated ring.

**System action:** `POST /api/pair` with device identifier. Guardian must be powered on and on the same network.

**Timeout:** If no response in 30 seconds, transition to the Failed state.

**Design note:** Show progress steps below the animation to reduce anxiety:

1. Guardian found on network
2. Verifying device identity...
3. Establishing secure connection...

---

### **Step 4 — Pairing Success (OB-04) or Failure (OB-05)**

**Success:** Marcus sees a green confirmation — Guardian name, device ID, and connection type are displayed. A subtle success animation plays. He taps **Continue**.

**Failure:** Marcus sees a clear error — *"Couldn't connect to Guardian."* Three options are shown:

* **Try Again** — Returns to Step 2
* **Get Help** — Opens the Quick Start guide
* **Skip for now** — Allows limited-mode entry (app works with cached/demo data, Guardian features disabled)

**Design note:** The Skip option should use subdued styling (not a primary button) to discourage it while still making it accessible. Field engineers should not be blocked from using the app just because the hardware is temporarily unavailable.

---

### **Step 5 — Account Setup (OB-06)**

Marcus either creates a new account or logs in to an existing one. The form is minimal:

* Email address
* Password (with show/hide toggle)
* "Create Account" or "Log In" toggle at the top

**System action:** On account creation, the backend auto-generates a DID (Decentralized Identifier) for this user tied to their Guardian device. Marcus does not need to understand this yet — it happens silently.

**Design note:** Password requirements shown inline as the user types (character count, number, special character). No separate "confirm password" field — use show/hide toggle instead to reduce friction.

---

### **Step 6 — DID Introduction (OB-07)**

This is a critical UX moment. Marcus sees his DID for the first time. Most users will not know what a DID is. This screen must:

1. **Explain it simply:** *"Your DID is your secure identity on this network. Share it with teammates so they can invite you to their Circles."*
2. **Show the DID string** in a monospace code block: `did:guardian:sgx05-ml4vwppi`
3. **Provide a Copy button** — one tap to copy the full DID to clipboard
4. **Confirm copy** — show "Copied\!" toast notification after tapping

A **"What is a DID?"** expandable section should be available for curious users, with a plain-language explanation of Decentralized Identifiers.

**Design note:** Do not overwhelm Marcus with cryptographic detail here. The message is simple: *"This is your ID. Copy it. Share it. That's all you need to know right now."*

---

### **Step 7 — Create First Circle (OB-08) — Optional**

Marcus is prompted to create his first Circle of Trust. This is framed as an optional but recommended step. The screen shows:

* A brief explanation: *"A Circle is your trusted group. Add your team's Guardian devices to share alerts, chat securely, and coordinate responses."*
* **Circle Name** input field (e.g., "Site Alpha Team")
* **Description** optional input
* **Create Circle** primary button
* **Skip for now** subdued link

If Marcus creates a Circle, the system generates a Certificate Authority, initializes the Circle network, and auto-adds his Guardian as the first member — all in the background while showing a subtle loading state.

**System actions:** `POST /api/circles` → Certificate Authority generation → Circle network initialization.

---

### **Step 8 — Onboarding Complete (OB-09)**

Marcus lands on a celebration screen summarizing what's been set up:

 Guardian connected — SGX-05
 Account created — marcus@energyco.com
 DID copied
 Circle created — "Site Alpha Team" (or "No circle yet — create one anytime")

Single CTA: **Go to Dashboard** (large purple button).

**Design note:** Keep this screen brief. Marcus wants to get to the dashboard. Don't add tutorials or tips here — that's what the Quick Start guide in Settings is for.

---

### **Step 9 — Home Dashboard (HM-01)**

Marcus lands on the redesigned dashboard. His Guardian is connected. The Health Score ring shows green. He's in.

Onboarding is marked complete in local storage — it will never show again for this user on this device.

## **API / System Dependencies**

| Step | API Call | Description | Failure Handling |
| ----- | ----- | ----- | ----- |
| 3 | `POST /api/pair` | Send pairing request with device QR/serial | Timeout → OB-05 Failed |
| 5 | `POST /api/auth/register` or `POST /api/auth/login` | Create or authenticate user account | Error → inline form error |
| 5 | DID auto-generated | Backend generates DID on account creation | Show retry if generation fails |
| 7 | `POST /api/circles` | Create Circle \+ generate Certificate Authority | Error → retry or skip |
| 7 | Circle network initialized | Guardian auto-joins as first member | Silent background action |

## **Design Notes**

| \# | Note |
| ----- | ----- |
| DN-01 | Bottom navigation bar is **hidden** throughout all onboarding screens. Users should not be able to navigate away mid-setup. |
| DN-02 | A **progress indicator** (step dots or step counter "2 of 5") should be visible during onboarding to give Marcus a sense of progress. |
| DN-03 | The **Skip** option in OB-08 (Create Circle) must be visually de-emphasized — use a text link, not a button. We want users to create a Circle but not block those who can't right now. |
| DN-04 | All form inputs must have **44px minimum touch targets** for field use. |
| DN-05 | The pairing QR scanner should show a **viewfinder overlay** with corner guides to help Marcus aim the camera accurately in poor lighting. |
| DN-06 | The DID string in OB-07 must use **JetBrains Mono** font and be displayed in a dark card with a subtle border — it should look like a technical credential, not plain text. |
| DN-07 | After successful pairing, store the Guardian connection in local/session storage so the app doesn't require re-pairing on every launch. |

## **Edge Cases**

| Edge Case | Scenario | Handling |
| ----- | ----- | ----- |
| EC-01 | Camera permission denied | Show inline instructions \+ fallback to serial entry |
| EC-02 | Guardian QR code damaged/unreadable | Fallback to serial number entry |
| EC-03 | Guardian not on same network | Error \+ suggestion to connect to same WiFi as Guardian |
| EC-04 | Guardian already paired to another account | Error message: "This Guardian is registered to another account. Contact your administrator." |
| EC-05 | Account email already exists | Inline error: "An account with this email already exists. Log in instead?" with login link |
| EC-06 | Weak password | Inline validation — show requirements as user types |
| EC-07 | Circle creation fails | Non-blocking error — "Circle creation failed. You can create one later in the Network tab." Continue to dashboard. |
| EC-08 | User closes browser mid-onboarding | On re-open: resume from last completed step (store progress in sessionStorage) |
| EC-09 | DID generation fails | Retry once automatically, then show error with "Try again" — DID is required for Circle invites |
