
# SG-X Guardian --- Task 4 Threat Prediction Model

## Plan 2 --- Production Wiring Plan (Deliverables D1--D11)

**Document purpose:** Define the production integration plan for the
already implemented Task 4 AI engine under
`crates/sgx-anomaly-engine/src/threat_prediction/`. This plan wires
Deliverables D1--D11 into the live SG-X Guardian runtime without
duplicating or replacing the AI engine.

**Repository root:** `~/SGX`

**Existing AI engine:**
`crates/sgx-anomaly-engine/src/threat_prediction/`

**Production integration root:** `src/task4_threat_prediction/`

---

# 1. Production Objective

Task 4 must operate as a real Guardian runtime service rather than only
as an isolated AI library/demo. The production flow will collect
security evidence from existing SG-X subsystems, normalize it into the
Task 4 event contract, run the D1--D11 prediction pipeline, persist
forecasts and evidence, expose status through the REST API, and hand
high-risk recommendations to the existing Task 2 Virtual Shift
owner-review lifecycle.

The production integration must preserve subsystem ownership:

- Task 1 remains the anomaly-detection owner.
- Suricata remains the IDS/network-alert owner.
- Discovery/NMAP remains the LAN device-discovery owner.
- Attestation remains the cryptographic trust owner.
- Circle/CoT/Nebula remain the membership and network-relationship
  owners.
- Task 3 remains the route/network-intelligence owner.
- Task 4 predicts future threats and generates advisory hardening
  recommendations.
- Task 2 remains the authorization and policy-application owner.
- Task 4 must **not directly apply nftables rules, quarantine peers,
  rotate identity, or alter policy**.

# 5. D1 --- Domain Models and Production Configuration Wiring

## Objective

Wire the D1 Task 4 domain/configuration types into the Guardian
production runtime.

## Existing AI component

- `crates/sgx-anomaly-engine/src/threat_prediction/model.rs`
- `crates/sgx-anomaly-engine/src/threat_prediction/config.rs`
- `crates/sgx-anomaly-engine/config/threat_prediction.json`

## Production work

Create `src/task4_threat_prediction/config.rs` as the production loader.
It should load the packaged/default Task 4 configuration and optionally
support a deployment override under `/etc/sgx-guardian/`.

Recommended runtime paths:

```text
/etc/sgx-guardian/threat-prediction/config.json
/var/lib/sgx-guardian/threat-prediction/
```

The loader must validate thresholds, horizons, temporal windows, queue
limits, retention settings, and feature enablement before the runtime
starts.

Configuration errors must fail Task 4 closed: the Guardian continues
running, but Task 4 reports a degraded/disabled state rather than
starting with unsafe implicit values.

## Wiring result

D1 becomes the single configuration/domain source used by every
production Task 4 adapter and runtime cycle.

# 6. D2 --- Canonical Security Event Production Ingestion

## Objective

Convert heterogeneous production evidence into the existing Task 4
`SecurityEvent` contract.

## Production files

- `collector.rs`
- `event_adapter.rs`
- `source_health.rs`

## Inputs

Events will be accepted from:

- Task 1 anomaly output
- Suricata threat alerts
- Discovery/NMAP deltas
- Attestation results/trust changes
- Circle/CoT/Nebula relationship changes
- Task 3 route/degradation context
- optional geographic threat intelligence

## Required controls

The collector must provide:

- bounded Tokio channel;
- non-blocking producers;
- event ID deduplication;
- timestamp/future-time validation;
- schema validation;
- source identity;
- source-health counters;
- dropped/lagged-event metrics;
- bounded in-memory history;
- no panic on malformed external data.

Suricata currently uses a broadcast feature tap, so Task 4 must
subscribe before live threat events begin flowing.

## Wiring result

Every production source reaches the prediction engine through one
normalized contract instead of Task 4 reading unrelated subsystem
internals directly.

# 7. D3 --- Task 1 Anomaly Bridge Wiring

## Objective

Feed real Task 1 anomaly evidence into Task 4 as precursor/context
evidence.

## Existing production source

- `src/task1_ai/scorer.rs`
- `src/task1_ai/runtime.rs`
- `AlertAnomalyScore`
- existing Task 1 full-ML alert persistence

## Production file

`src/task4_threat_prediction/task1_adapter.rs`

## Integration design

The adapter must translate Task 1 anomaly output into the D3 bridge
format already implemented in the AI crate. It must preserve:

- node identity;
- observation timestamp;
- anomaly score;
- threat category;
- confidence/context where available;
- source/evidence identifier.

Task 1 remains responsible for detecting current anomalous behavior.
Task 4 uses that evidence only to estimate future threat probability.

Do not duplicate Task 1 scoring inside Task 4.

## Trigger behavior

A sufficiently significant Task 1 anomaly can request an immediate Task
4 evaluation, subject to debounce. Normal Task 4 periodic evaluation
continues independently.

# 8. D4 --- Temporal Pattern Engine Production Wiring

## Objective

Supply real event history to D4 so time-of-day frequencies, event rates,
burst behavior, and historical windows are based on live Guardian
evidence.

## Production integration

`runtime.rs` owns the bounded Task 4 event state. D4 receives snapshots
of valid normalized events.

The runtime must preserve chronological ordering and reject or isolate
invalid future timestamps.

Historical windows must come from D1 configuration. Prediction horizons
are not scheduling intervals; a two-hour horizon means "risk within the
next two hours," not "run every two hours."

## Persistence/recovery

Recent normalized evidence required for prediction continuity should be
persisted in a bounded append-only form and restored at startup within
the configured retention/window limits.

Suggested file:

```text
/var/lib/sgx-guardian/threat-prediction/events.jsonl
```

The runtime must cap both disk retention and in-memory event count.

# 9. D5 --- Sequence and Precursor Detection Wiring

## Objective

Run D5 against real ordered production evidence to identify attack
precursors and attack-type sequences.

## Production evidence examples

- reconnaissance or scan evidence from Suricata;
- unauthorized/drifted devices from Discovery;
- unusual Task 1 traffic/anomaly scores;
- repeated protocol violations;
- failed or deteriorating peer attestation;
- route degradation/exposure from Task 3;
- peer compromise evidence from Circle-related members.

D5 consumes normalized events only. It should not directly call NMAP,
Suricata, or the attestation service.

## Event-driven behavior

When a newly ingested event completes a configured precursor sequence,
the runtime may request a debounced immediate forecast cycle.

This keeps detection responsive without creating one prediction cycle
for every packet/alert.

# 10. D6 --- Threat Predictor Production Execution

## Objective

Execute the existing D6 predictor using D4/D5 features and current
production context.

## Runtime responsibility

`runtime.rs` orchestrates:

```text
validated events
    → temporal features
    → precursor/sequence features
    → predictor
    → candidate threat forecasts
```

The runtime must isolate prediction failures from the Guardian process.
A failed prediction cycle should:

1. record the error;
2. mark runtime/source health;
3. preserve previous valid forecast state according to lifecycle rules;
4. retry on the next cycle/event;
5. never apply security policy as a fallback.

## ML acceptance note

Production wiring does not replace D6's prediction implementation. If D6
is currently heuristic/weighted rather than a trained predictive model,
production wiring can still integrate it, but the original "ML threat
prediction model" acceptance requirement remains a separate
model-training/model-artifact gap until a trained model is introduced.

# 11. D7 --- Circle-Wide Peer Cascade Production Wiring

## Objective

Provide D7 with real relationship/exposure evidence so peer compromise
risk is correlated safely.

## Production file

`circle_adapter.rs`

## Existing sources

- `src/circle/members.rs`
- `src/circle/model.rs`
- `src/nebula/overlay_registry.rs`
- `src/nebula/relay_registry.rs`
- Task 2 peer routing-trust summaries from attestation

## Correlation rule

Circle membership alone must **not** imply equal compromise exposure.

The adapter should combine evidence such as:

```text
Circle membership
+ active lifecycle state
+ Nebula overlay relationship
+ relay/shared-route relationship
+ attestation/trust state
+ freshness
= cascade exposure context
```

Example:

```text
Peer A compromised
    ↓
Is Peer B an active Circle member?
    ↓
Does A/B have meaningful shared network/relay/exposure evidence?
    ↓
Is evidence fresh and trusted?
    ↓
Yes → elevate B cascade risk proportionally
No  → do not blanket-elevate B
```

This prevents one compromised member from automatically marking the
entire Circle as high risk.

# 12. D8 --- Confidence, Calibration, Source Health and Geo Wiring

## Objective

Ensure production forecast confidence reflects evidence quality,
freshness, and source availability.

## Production files

- `source_health.rs`
- `geo_intel_adapter.rs`

## Source health

Track at least:

- last successful event timestamp;
- lag/dropped-event count;
- parse/validation failures;
- stale source state;
- enabled/disabled state.

A high predicted probability with poor evidence health must not be
presented as equally trustworthy as a well-supported prediction.

## Geographic intelligence

Geo intelligence is optional context, not an autonomous enforcement
source.

Required controls:

- provenance/source identifier;
- retrieval/observation timestamp;
- TTL/freshness;
- confidence;
- no country-only high-impact security decision.

If geo intelligence is unavailable, Task 4 continues using local
evidence and reports reduced context rather than failing the Guardian.

## Objective

Turn D9 forecasts into durable production objects with lifecycle

## Production files

- `persistence.rs`
- `audit.rs`

```text

├── events.jsonl
```

Writes for current-state JSON files must be atomic

## Forecast lifecycle

Production runtime should preserve D9 lifecycle semantics such as
creation, refresh/update, expiry, resolution, supersession, and
recommendation linkage.

Forecast IDs must remain stable according to the D9 contract so
duplicate evaluations do not create repeated owner-review requests for
the same forecast state.

## Audit evidence

Each persisted forecast should be traceable to:

- prediction timestamp;
- horizon;
- target node/peer;
- threat type;
- probability;
- confidence;
- precursor/evidence references;
- source-health snapshot;
- Task 2 recommendation/handoff state.

# 19. Scheduler and Runtime Execution Model

## Periodic evaluation

Recommended default production cycle:

```text
every 5 minutes
```

This is the prediction evaluation cadence, not the prediction horizon.

## Immediate/debounced evaluation triggers

Allow a quicker recalculation after:

- high-value Task 1 anomaly;
- high/critical Suricata evidence;
- relevant discovery delta;
- attestation failure/trust restriction;
- peer compromise/cascade event;
- meaningful Task 3 network-context change.

Use a debounce window so bursts of related events collapse into one
prediction cycle.

## Tokio design

Use:

- one bounded `mpsc` ingestion channel;
- one collector/event-state task;
- one scheduler/evaluation task;
- source adapters as lightweight producers;
- `spawn_blocking` only if the D6 predictor becomes CPU-heavy enough
  to block Tokio worker threads.

Do not hold unrelated Guardian locks across prediction work or sleeps.

# 24. Backpressure and Failure Handling

Production wiring must explicitly handle:

## Channel saturation

Do not block Suricata, Task 1, Discovery, or attestation producers
indefinitely. Record dropped-event counters and source degradation.

## Broadcast lag

Suricata lag must be visible in source health.

## Disk failure

Forecasting may continue temporarily in memory according to configured
policy, but persistence failure must be visible and Task 2 handoff must
not claim durability when persistence failed.

## Task 2 unavailable

Persist the forecast/recommendation and retry the handoff idempotently.
Do not bypass owner approval.

## Task 3 unavailable/stale

Continue prediction with Task 3 context marked unavailable/stale and
adjust confidence according to D8.

## Circle/attestation unavailable

Do not fabricate peer exposure. Cascade confidence should decrease or
cascade evidence should be omitted.

# 25. Security Requirements

The production integration must enforce these rules:

- no direct policy enforcement from Task 4;
- no untrusted event may cause a panic;
- no blanket peer compromise based only on Circle membership;
- no country-only geo enforcement;
- no stale evidence treated as fresh;
- no duplicate owner-review flooding;
- no unbounded event/history memory;
- no blocking external subsystem while Task 4 predicts;
- no route control from Task 4;
- no re-attestation trigger directly from Task 4;
- all high-impact changes remain behind existing Task 2 owner/admin
  approval and signing.

# 32. Definition of Done for D1--D11 Production Wiring

Production wiring is complete when:

- all D1--D11 AI components are invoked from the live Guardian
  runtime;
- Task 1, Suricata, Discovery, attestation, Circle/Nebula and Task 3
  evidence reaches Task 4 through explicit adapters;
- forecasts are durable, queryable, auditable and recoverable;
- peer cascade uses real relationship/exposure evidence rather than
  blanket Circle membership;
- confidence reflects stale/missing/degraded sources;
- D10 creates idempotent Task 2 owner-review handoffs;
- Task 4 cannot directly apply security policy;
- existing Task 2 approval/sign/gossip/apply controls remain
  authoritative;
- Task 3 remains routing owner;
- bounded queues/history prevent resource growth;
- startup/restart/failure behavior is tested;
- REST APIs expose forecast/runtime/source-health state;
- formatting, compilation and production integration tests pass.
